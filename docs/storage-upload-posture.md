# Storage Upload Posture (Current Implementation)

## Current state

The API currently uses the local file storage provider and serves uploads directly from the API process.

Evidence:
- File handler: `services/api/internal/handler/files/handler.go`
- Local provider: `services/api/internal/foundation/filestore/local.go`
- Static serving: `services/api/cmd/api/main.go` (`/uploads/*`)

## Security posture (current)

- Upload API is authenticated and rate-limited (`RateLimitByKey("upload", ...)`)
- Files are written under local `UPLOAD_DIR`
- Public URLs are returned as `/uploads/<key>.<ext>`
- Uploaded files are therefore **publicly retrievable** if the URL is known

## Operational implications

- Suitable for single-node/dev/staging deployments
- Not ideal for production multi-node/object-storage setups
- No signed URL expiry model in current implementation

## Recommended production controls until S3/signed URLs are added

1. Put the API behind a trusted reverse proxy / WAF.
2. Restrict upload MIME types and sizes at edge + API.
3. Use non-guessable object keys (already generated by server).
4. Avoid storing highly sensitive documents unless access model is reviewed.
5. Consider isolating uploads on a dedicated domain with security headers.

## Roadmap

- Add S3-compatible storage backend
- Add signed URLs for private files
- Add per-file access policy enforcement for sensitive document classes
